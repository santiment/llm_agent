# Slash Commands — Plan v2

Crypto/market research commands for the Deep Research Agent. v2 supersedes the v1
plan after review (see `FEATURES_PLAN.md`, "Verdict on COMMANDS_PLAN.md"): same
registry/macro core, but the **expansion moves inside the graph**, the catalog grows a
**market-wide tier** (what's hot, trends, screening), and the plan names the **new
tools** those commands need. Control/config commands (`/watch`, `/model`, `/budget`)
are dropped from this repo — they belong to the backend (Oban cron) and the UI
(configurable overrides).

## What changed from v1, and why

| v1 | v2 | Why |
|----|----|-----|
| Dispatch in `examples/client.py` | `CommandExpansionMiddleware` inside the graph | The Python client is a dev tool; the production surface is the sanbase LiveView. Expanding server-side means **every** client (sanbase, `examples/client.py`, Studio, raw SSE) gets commands with zero client code. |
| `/watch` interval loop in the client | Out of scope → sanbase Oban job per saved watch, fresh thread per tick | An in-terminal loop dies with the terminal; schedules must be durable and per-user. |
| `/model`, `/budget`, `/depth`, `/timeframe` client commands | Out of scope → UI controls setting `configurable` keys | They are one-line config overrides, not research commands. |
| 9 asset-scoped commands | + 6 market-wide commands (`/hot`, `/brief`, `/screen`, `/movers`, `/narratives`, `/sector`) | The agent must answer "what is hot on crypto **right now**", not only "tell me about asset X". |
| Tools assumed sufficient | New-tools section: `web_fetch`, `market_snapshot`, news-mode search, **current-date injection** | Market-pulse commands fail without them (detail below). |

Kept from v1 unchanged: the sync registry + parser core (`registry.py`, `parse.py`),
hand-rolled frontmatter (no pyyaml), file-based commands in `commands/*.md`,
`$ARGUMENTS`/`$1..$9` substitution, path-guard so `/Users/...` is never treated as a
command, built-ins-win collision rule, sync standalone-runnable tests.

## Architecture v2 — expansion inside the graph

A new middleware, first in the chain:

```
src/deep_research_agent/commands/
  __init__.py      # load_file_commands(), expand(), is_command_message()
  registry.py      # registry dict, frontmatter meta, is_command()   (v1 code, as-is)
  parse.py         # split_command(), substitute()                   (v1 code, minus parse_interval)
  middleware.py    # CommandExpansionMiddleware
commands/          # user-authored command defs (markdown), project root
```

`CommandExpansionMiddleware.before_agent` (runs once per turn, before the model):

1. Take the current turn's first `HumanMessage`. If it doesn't match
   `^/[A-Za-z][\w-]*(\s|$)` → do nothing (the path guard from v1: `/Users/x` has `/`
   inside the token and fails `is_command`).
2. Known command → replace the message content with the expanded template
   (`substitute(body, args)` + the shared style footer, below). The model only ever
   sees expanded text — same invariant as v1.
3. `/help` or `/commands` → deterministic reply: jump to `end` with an AIMessage
   listing every registered command + its `description` and `argument-hint`. No model
   call, no cost. (Same `hook_config(can_jump_to=["end"])` pattern as
   `BudgetMiddleware`.)
4. Unknown `/name` (no inner `/`) → jump to `end` with "unknown command: /name — try
   /help". Deterministic, mirrors v1's client behavior.

Wiring in `agent.py`: load the registry once per `make_graph` from
`cfg.commands_dir` (new config field, default `<repo>/commands`, env
`DRA_COMMANDS_DIR`, configurable `commands_dir`), prepend the middleware to the
`middleware` list. If the dir is absent the middleware is skipped — degrades to
current behavior, like skills.

What clients need to do: **nothing**. Sanbase keeps POSTing the raw user text.
For autocomplete chips in the LiveView, expose the catalog as data: a tiny
`commands/manifest.json` generated by a `./run.sh commands` task (name, description,
argument-hint, tier) that sanbase reads at deploy — no live endpoint needed.

Why middleware and not client-side (the v1 doubt, answered): one implementation, all
clients; templates version with the agent and its prompts (they reference tool names —
they *belong* with the agent); `/help` stays deterministic via jump-to-end; and the
graph remains untouched for non-command input.

## Command catalog v2

Three tiers. **Market tier is new** — it answers "what's hot", "what's moving",
"what's the narrative" with no asset argument. Tool names are the MCP tools the agent
already gets from the Santiment server (`fetch_metric_data`, `assets_by_metric`,
`combined_trends`, `trending_stories`, `fetch_insights`, `insight_discovery`,
`metrics_and_assets_discovery`) plus `web_search` and the new tools below.

### Market tier (new) — market-wide pulse, no asset required

| Command | Purpose | Key tools | Shape |
|---------|---------|-----------|-------|
| `/hot [topic]` | What is hot in crypto right now: trending assets, words, stories, social spikes — each validated against on-chain reality | `trending_stories`, `combined_trends`, `assets_by_metric` (social volume / price change), sub-agent per top trending asset | full report, fan-out |
| `/brief` | Daily market brief: global snapshot, BTC/ETH state, top movers, dominant narratives, dated catalysts ahead | `market_snapshot` (new), `assets_by_metric`, `trending_stories`, news search | full report |
| `/screen <metric> [N] [asc]` | Rank assets by any metric, top-N table + outliers worth a look | `metrics_and_assets_discovery` (resolve metric), `assets_by_metric` | fast report |
| `/movers [24h\|7d]` | Top gainers/losers; separate moves with substance (on-chain + social confirm) from noise | `assets_by_metric`, `fetch_metric_data`, `combined_trends`, sub-agent per top mover | full report, fan-out |
| `/narratives` | The narrative map: which stories are rising / peaking / fading, the assets attached to each | `combined_trends`, `trending_stories`, `fetch_insights`, news search | full report |
| `/sector <name>` | Sector roundup (DeFi, L2, AI, memes…): constituents, relative performance, leaders/laggards | `assets_by_metric`, `fetch_metric_data`, web | full report |

The fan-out pattern (`/hot`, `/movers`) is the agent's existing strength used
deliberately: the orchestrator pulls the trending/mover list cheaply, then spawns one
`research-subagent` per top asset *in parallel* to answer one question each — "is this
move backed by on-chain activity, or is it hollow hype?" — and synthesizes a ranked
verdict. This is exactly the unit-per-sub-agent partitioning `agent.py` is built
around, and with FEATURES_PLAN #1 (cheap sub-agent model) each validation costs
pennies.

Representative template — `commands/hot.md`:

```markdown
---
description: What's hot in crypto right now — trending assets, narratives, social spikes, validated on-chain
argument-hint: [topic (optional — default whole market)]
tier: market
---
Find what is hot in crypto RIGHT NOW. Scope: $ARGUMENTS (if empty: the whole market).

Today's date is in your context — "now" means the last 24-72 hours, not your training data.

1. Pull the pulse: trending_stories and combined_trends for trending assets, words and
   stories; assets_by_metric for top social-volume spikes and 24h price movers. Web-search
   recent news for anything the data tools surface but don't explain.
2. Take the top 3-5 genuinely hot items. Spawn ONE research-subagent per item, in
   parallel, each answering: what is the story, when did it start, is it confirmed
   on-chain (active addresses, exchange flows, whale moves) or social-only hype?
3. Deliver a cited report via submit_report:
   - A ranked HEAT LIST: item, the narrative in one line, how hot (social volume vs
     baseline), since when
   - Per item: substance verdict — on-chain confirmed / hype-only / too early to tell,
     with the evidence
   - What is FADING (was hot last week, cooling now)
   - One paragraph: the market's dominant mood right now
```

### Asset tier (existing 9, upgraded)

`/analyze`, `/sentiment`, `/onchain`, `/news`, `/metric` (one-shot) and `/thesis`,
`/risk`, `/dd`, `/compare` (decision-support) stay as written in `commands/*.md`.
Upgrades applied to all:

- **Timeframe argument.** Every asset command accepts an optional trailing timeframe
  token (`/analyze BTC 90d`). Templates gain "Timeframe: $TIMEFRAME" where the
  expander substitutes a recognized trailing `\d+[dwmy]|ytd` token, else the default
  (`commands_default_timeframe`, configurable, default `30d`). Pure parse-time work in
  `parse.py` — no new model behavior to trust.
- **Shared style footer.** "Analysis, not financial advice", citation reminders, and
  "aggregate, never transcribe" are repeated per file today. The expander appends
  `commands/_style.md` to every expansion instead; templates keep only what is
  specific to them. One place to tune the house voice.
- **Depth flag.** `--deep` anywhere in args strips the flag and appends
  `commands/_deep.md` ("spawn sub-agents per angle, full report, stress-test the
  conclusion"); default stays fast. Honest limitation: this steers *behavior via
  prompt* only — budgets (`max_tool_calls` etc.) are fixed at `make_graph` time and a
  flag inside a message cannot raise them. Budget-level depth remains a `configurable`
  knob for the UI.
- `/news` and `/sentiment` should name the news-mode search explicitly once it exists
  (below): "use news search with days=7" instead of hoping general search returns
  fresh items.

### Frontmatter v2

```
description, argument-hint   (v1)
tier: market | asset | decision   (manifest + UI grouping)
depth: fast | full                (default report shape; --deep overrides)
```

## New tools the catalog needs

The market tier is only as good as its inputs. Four additions, in priority order:

1. **Current-date injection — required, trivial, do first.** Nothing in `prompts.py`
   tells the model today's date. "What is hot *right now*" with an undated model
   yields confidently stale answers from training data. Fix in `make_graph`: prepend
   `f"Current date: {datetime.now(UTC):%Y-%m-%d}"` to both orchestrator and sub-agent
   prompts. (This is a bug for the *existing* agent too, independent of commands.)
2. **`tools/market.py` — `market_snapshot`.** One call returning the market-wide
   frame the Santiment MCP doesn't provide as a single shot: global market cap +
   24h change, BTC dominance, total volume, fear & greed index, top-10 by cap with
   24h/7d change. Sources: CoinGecko free API (`/global`, `/coins/markets`,
   `/search/trending`) + alternative.me F&G — no API keys, no new deps beyond httpx.
   Emits `mcp_call`-style events so the UI renders it. `/brief` and `/hot` lead with
   it; without it they burn 10+ calls reconstructing the frame.
3. **News-mode search.** Tavily supports `topic="news"` + `days=N`. Add either a
   `days`/`topic` parameter on `web_search` or a separate `news_search` tool
   (recommended: separate tool, clearer for the model). `/news`, `/brief`, `/hot`,
   `/narratives` all want "last N days, news only" rather than evergreen SEO pages.
4. **`web_fetch`** — already FEATURES_PLAN #3. Market commands inherit it: reading
   the actual announcement/post behind a trending story instead of citing a snippet.

Explicitly *not* needed: a screener tool (`assets_by_metric` already ranks), a social
tool (`combined_trends`/`trending_stories` cover it), price OHLC (`fetch_metric_data`).

## Scheduling (out of this repo, restated)

`/brief` every morning and `/hot` on an interval are the obvious cron targets — as
**sanbase Oban jobs** over persisted threads (FEATURES_PLAN #7): durable, per-user,
survives restarts, results land in the saved-thread UI. The agent side needs nothing:
a scheduled run is just a normal run whose input is `/brief`. This replaces v1's
in-client `/watch` loop entirely.

## Phases

1. **Core (v1 code, relocated).** `registry.py` + `parse.py` + file loader under
   `src/deep_research_agent/commands/`, sync, with v1's tests (minus
   interval/watch/session tests). Plus `$TIMEFRAME` + `--deep` + style-footer
   expansion rules.
2. **Middleware.** `CommandExpansionMiddleware` (expand / help / unknown jump-to-end),
   `commands_dir` config field, wiring in `agent.py`, date injection in prompts.
   Done when: POSTing `/analyze BTC` through the LangGraph API (any client) runs the
   expanded prompt; `/help` returns the catalog without a model call; `/Users/x/y`
   passes through untouched.
3. **New tools.** `market_snapshot`, `news_search`, (web_fetch tracks FEATURES_PLAN
   #3 separately). Done when `/brief` produces a dated brief with global numbers in
   one tool call's worth of framing.
4. **Catalog v2.** Six market-tier files (`hot.md`, `brief.md`, `screen.md`,
   `movers.md`, `narratives.md`, `sector.md` — see `commands/`), `_style.md` +
   `_deep.md` includes (loader must skip `_*.md` as commands), trims of the
   existing 9 to use the shared footer, `manifest.json` generation.
5. **Tests.** v1's sync test list (split/substitute/dispatch/file-loader/collision)
   plus: timeframe extraction, `--deep` stripping, `_*.md` exclusion, middleware
   expansion on a fake state, `/help` jump payload, market_snapshot normalizer
   (fixture JSON, no network).

No new runtime deps (httpx ships with the stack; frontmatter stays hand-rolled).

## Confidence

- Registry/parse core: **high** — unchanged v1 design, already reviewed.
- Expansion middleware incl. jump-to-end `/help`: **high** — same hook pattern as
  `BudgetMiddleware` (`hook_config(can_jump_to=["end"])`), and `turn.py` already
  scopes turns, which the middleware reuses to find "first message of this turn".
- Market catalog value: **high** — it targets exactly the questions the user asks the
  product ("what's hot", trends, movers) and rides existing MCP tools.
- `market_snapshot` via CoinGecko free tier: **medium-high** — free-tier rate limits
  are real (~10-30 req/min); one snapshot call per run is comfortably inside them,
  but add a short TTL cache (FEATURES_PLAN #4 covers it) before any cron usage.
- `--deep` as prompt-level depth only: **high** that it works as specified; budget
  changes stay out of scope by design.
